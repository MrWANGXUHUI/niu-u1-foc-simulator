# 小牛 U1 FOC 模拟器 — 项目笔记

> 板子: 天问 Pro TW002 (ESP32-C3-DevKitC-02 + CH340K)
> 串口: 485 → V35 ECU (8E1 9600),  UART0 (`/dev/ttyUSB0`) → 调试日志
> 上次更新: 2026-10-30 (蓝牙优先架构: WiFi 默认关, 蓝牙遥控开热点; 广播包名字放主广播包)

## 1. 硬件接线 (当前)

| 功能 | GPIO | 备注 |
|---|---|---|
| 485 TX | GPIO 7 | MAX485 DI (自动收发模块, 无 DE/RE 引脚) |
| 485 RX | GPIO 4 | MAX485 RO |
| OLED SDA | GPIO 5 | 板载 SSD1306 128×64, 地址 0x3C |
| OLED SCL | GPIO 6 |  |
| 霍尔轮速 | GPIO 3 | 1 磁钢, 轮周长 1.28m (16x2.50/64-305 实测), **INPUT_PULLUP + 下降沿中断**. 测速用**脉冲间隔** (单磁钢下计数窗口会乱跳), 2s 无脉冲判停转 |
| 调试口 | UART0 | CH340K 接 UART0 (GPIO20/21), `/dev/ttyUSB0` 115200 8N1 |

> ⚠️ **GPIO 9 是 ESP32-C3 的 BOOT 脚**, 不要当普通 GPIO 用. 刷机脚本能自动进下载模式 (见 §4), 手动按 BOOT 只作备用.

> ⚠️ **霍尔传感器必须上拉**: A3144/SSR14Y 都是开集电极 (open-collector) 输出, 内部晶体管关断时输出脚是浮空的,
> 不上拉会读到随机噪声脉冲, 轮速全是乱跳. 代码里用 `pinMode(WHEEL_SPEED_PIN, INPUT_PULLUP)` 打开 ESP32 内部上拉
> (~45kΩ). 如果干扰大或线长, 建议外挂 4.7k~10k 上拉电阻. 磁铁经过时输出被拉低 → **下降沿中断 (FALLING)**.

## 2. 串口与日志

- **485 总线**: 必须在 `Serial1.begin(9600, SERIAL_8E1, 4, 7)`, **不是** 115200 8N1. 错配 1 位都收不到 V35 报文.
- **调试口**: `Serial.begin(115200)`, 仅作调试日志镜像, 不影响 485 总线.
  ⚠️ **`platformio.ini` 里的 `-DCDC_ON_BOOT=1` 对 ESP32-C3 无效** —— Arduino core 2.0.17 只认
  `ARDUINO_USB_CDC_ON_BOOT` (默认 0), 认错了宏, 所以 `Serial` **就是 UART0**, 不是原生 USB.
  板子上的 CH340K (`/dev/ttyUSB0`) 正好接 UART0, 所以**应用日志就在 `/dev/ttyUSB0` 上**
  (ROM 启动日志 `rst:0x1 (POWERON)` 也从这儿出来).
  要改成原生 USB: 把宏换成 `-DARDUINO_USB_CDC_ON_BOOT=1`; 但那之后 `Serial.flush()` 在"电脑接上但没人读"
  时可能长时间阻塞, 而 V35 单次轮询超时只有 ~20ms —— 改之前先把应答路径上的 flush 都去掉.
- **minicom**: 默认不补 CR, 看到 "楼梯" 是正常的, 按 `Ctrl+A U` 打开 "Add Carriage Return" 即可.
- **日志刷屏**: `platformio.ini` 里 `CORE_DEBUG_LEVEL=3` (INFO), `log_v/log_d` 在编译期被替换成 `do {} while(0)`.
  关键: Arduino-ESP32 的 `log_v()` 走 `log_printf` 不走 `ESP_LOGV`, 所以 `esp_log_level_set()` 对它无效, 只能编译期关.

## 3. 485 协议 (V35 ECU 私有协议, DL/T 645 衍生)

帧格式: `68 [DEST_PAIR] 68 [FUNC] [LEN] [DATA+33...] [CHECKSUM] 16`

| 设备 | 地址对 (字节 1+2) |
|---|---|
| FOC 控制器 (本机) | `0x20 / 0xDF` |
| V35 中控 (主节点) | `0x40 / 0xBF` |
| 仪表 | `0x10 / 0xEF` |
| 电池 BMS | `0x31 / 0xCE` |

**关键点**:
- 字节 1+2 标识"这一帧说的是谁": 请求帧 = 目的设备, **应答帧 = 回话设备自己**.
  真车抓包: BMS 回 `31 CE`、仪表回 `10 EF`、FOC 回 `20 DF` —— FOC 应答一律用 `0x20 0xDF`.
  (代码里 `REPLY_WITH_ECU_ADDR` 想改成回 `0x40 0xBF` 时把它设成 1)
- 协议里**没有发送方地址字段** (因为 485 半双工总线隐式知道谁在说话)
- 数据区每个字节发送时 `+0x33` 混淆, 接收时 `-0x33` 反混淆
- 校验和 = 从字节 0 累加到 (不含) CS 字节, 取低 8 位 — **简单 sum & 0xFF**, 不是 CRC
- 轮询周期: V35 大约每 200ms 问一次 FOC

**已验证的示例帧** (Bilibili cv39475428 文章 7 条):
```
FOC read voltage     68 20 DF 68 01 01 38 09 16  (CS=0x09)
FOC read current     68 20 DF 68 01 01 3C 0D 16  (CS=0x0D)
ECU set master       68 40 BF 68 06 01 02 D8 16  (CS=0xD8)
Dashboard display    68 10 EF 68 04 0F ... 33 71 16  (CS=0x71)
... 全部用 sum & 0xFF 对得上
```

**我们 FOC 的应答** (2026-10 按真车抓包 + xzfn 的 ECU 源码对齐):

状态查询 `0x02 05 08` → 12 字节 (`0x05 09` → 14 字节, 多 2 字节 `00 02`):
```
68 20 DF 68 82 0C [30 26 3C 01 00 19 00 00 00 SS 08 00 → +0x33] [CS] 16
                                 └flag_0  保留 保留 保留 保留 保留 │ └SS=车速协议值(0-127) [9]  └flag_1(0x08=驻车) [10]
```
字段定义来自 `niu-ecu/User/niu_series_u.h` 的 `struct PayloadFOCInfoResponse`
(长度必须正好 12, 否则 ECU 判定通信失败并报错误码 190)。线性刻度: 协议值 = round(kmh×25/12), 范围 0..127;
ECU 换算: 仪表速度 = 车速值×12/25。

控制帧 `0x01` 的子命令 (原厂 FOC 的固定应答):
| 子命令 | 应答 | 说明 |
|---|---|---|
| `0x01` | `0x81` + 1 字节 `00` | 状态标志 |
| `0x02` | `0x81` + 16 字节 ASCII | 版本串 `U1E02V11U1E02V11` |
| `0x03` | `0x81` + 16 字节 ASCII | MU 编号 `MU00001B00000001` (兼作解锁命令) |
| `0x04` | `0x81` + 1 字节 `11` | 固件版本 |

系统配置 `0x06` → `0x86` + **空数据** (原厂就是空 ACK)。

## 4. 刷机流程

> **2026-10-29 实测: 不用手动按 BOOT 了.** `tools/flash.sh` 用 esptool 的
> `--before default_reset --after hard_reset`, 通过 CH340 的 DTR/RTS 就能自动把板子拨进下载模式.
> 2026-10-29 连续刷了三次都是一次成功 (2026-10-20 那会儿记的是"必须手动按 BOOT", 现在不成立了).
> 脚本本身还有 30 次重试, 万一自动进不去, 再按老办法手动按 BOOT 也不迟.

```bash
# 直接跑就行
bash tools/flash.sh /dev/ttyUSB0
```

手动进下载模式的备用办法 (自动复位失灵时):

```bash
# 1. 拔 USB
# 2. 按住 BOOT 不放
# 3. 插回 USB (设备进入下载模式)
# 4. 立刻跑 (脚本会持续轮询 30 次连接)
bash tools/flash.sh /dev/ttyUSB0
# 5. 看到 "Writing at 0x..." 进度 → 松开 BOOT
# 6. "Hard resetting via RTS pin..." → 完成
```

`tools/flash.sh` 一次性写 bootloader + 分区表 + app:

```
0x0     bootloader.bin
0x8000  partitions.bin
0x10000 firmware.bin
```

写之前还会先擦掉 **otadata** (0xE000, 0x2000):
改了分区表之后必须这么干 —— 旧的 otadata 还记着"从 app1 启动", 而 app1 在新分区表下
是没刷过的垃圾, bootloader 照着 otadata 去启动它, 表现为"刷完不启动".
擦成全 0xFF 之后 bootloader 找不到有效 otadata, 就退回启动第一个 app 槽 (app0).

`platformio.ini` 里 `board_build.flash_size = 4MB` (TW002 实际是 4MB flash, 不是 8MB).

### ⚠️ 分区表已改成 A/B 双槽 (2026-10-27, 2026-10-28 扩容)

`partitions.csv` 原来是单个 `factory` 分区, **没有 ota_0/ota_1, 根本没法 OTA**.
现在:

```
nvs,      data, nvs,     0x9000,  0x5000,
otadata,  data, ota,     0xe000,  0x2000,
app0,     app,  ota_0,   0x10000, 0x1D0000,
app1,     app,  ota_1,   0x1E0000, 0x1D0000,
coredump, data, coredump,0x3B0000, 0x50000,
```

每槽 1.75MB. **为什么这么大**: 加了 BLE 之后固件 1.58MB ——
Arduino-ESP32 自带的 Bluedroid 蓝牙协议栈一个人就占 ~700KB (WiFi+WebServer+OLED 再加 ~840KB),
1.5MB 的槽装不下. 取消了 spiffs (这个项目不存文件), 空间全给了 app 槽.

**改过分区表之后必须全量重刷一次** (上面那条 flash.sh 就是全量的),
老固件 (factory 分区) 没有 OTA 目标分区, 刷不进新固件.

## 5. 当前 setup() 顺序 (2026-10-30 版)

```
1. Serial.begin(115200)            # 调试日志 (UART0)
2. Wire.begin(5, 6) + setClock(400k) # ← 关键! 必须最早, 防止 u8g2 首刷时 Wire lock 还没创建
3. Serial1.begin(9600, 8E1, 4, 7)  # 485 总线 (RX=4, TX=7)
4. esp_log_level_set(*)            # 静音 ESP-IDF
5. simulator.begin()               # 霍尔 ISR (INPUT_PULLUP + FALLING)
6. u8g2.begin()                    # OLED
7. disp_lock = xSemaphoreCreateMutex() + xTaskCreate(oledTask)   # 画屏挪到独立任务
8. otaService.begin()              # 只注册 HTTP 路由, **不开热点** (WiFi 默认关, 见 §6.7)
9. bleTelemetry.begin()            # BLE GATT 服务 (再放最后, bluedroid 启动要几百 ms + 几十 KB 堆)
10. bleTelemetry.setApToggle()     # 把"开/关热点"的实现注入给蓝牙命令通道
```

`loop()` 里在 `updateWheelSpeed()` 之后调 `otaService.handle()` 和 `bleTelemetry.handle()` (都非阻塞).

> ⚠️ **热点不能开机就开** (2026-10-30): 开了之后 BLE 广播会被共存调度影响, 而且手机一连热点就断网.
> 现在的做法是 `otaService.begin()` 只注册路由, 真正开热点等小程序发蓝牙命令 (§6.7).
> 另外 `server.begin()` **必须等 WiFi 栈起来才能调** —— WiFi 从没初始化过就开监听会
> `tcpip_send_msg_wait_sem: Invalid mbox` 反复 panic, 所以挪到了 `startAP()` 里面.

## 5.0 OLED 必须跑在独立任务里 (2026-10-29 改, 关键)

**画屏绝不能放在 `loop()` 里.** 一屏 1024 字节, I2C 100kHz 下要传 ~95ms; 放在 loop 里的话
这 95ms 里 loop 完全动不了 —— 而 V35 单次轮询的超时只有 ~20ms, 撞上了就是
"这一轮没应答 → 错误码 190 → 车速 0", 也就是**"有时候没有速度"**.

同一个原因还会连带毁掉另外两件事 (2026-10-29 用户报"wifi 连不上 + 屏幕一会亮一会不亮"):

- `otaService.handle()` (WebServer) 也在 loop 里 → loop 被占 95% 的时间,
  HTTP 服务基本没法响应 → **手机连得上热点却发不出请求**
- 屏幕内容在"正常车速 / 错误码 190"之间来回变 → 看着就是**屏幕在闪**

现在的做法:

| 项 | 值 | 为什么 |
|---|---|---|
| 任务 | `oledTask`, 优先级 1 (跟 Arduino 的 loop 任务同级) | 同级靠时间片轮转, 不会饿死 loop |
| 栈 | 4096 字节 | u8g2 缓冲在堆上, 栈够用 |
| 周期 | 200ms | |
| I2C | 400kHz | 1024 字节从 95ms 降到 ~25ms |
| 数据传递 | loop 每 100ms 把快照写进 `disp_state` (互斥量保护), OLED 任务自己读 | loop 里绝不做 I2C |

另外 **`#define U8X8_DO_NOT_SET_WIRE_CLOCK` 必须在 include u8g2 之前** ——
u8g2 每传一页都会调一次 `Wire.setClock(100000)`, 不定义这个宏的话,
我们设的 400kHz 每次都被它改回 100kHz.

台架实测 (模拟 V35 每 200ms 发一帧): 显示满负荷重画时, 应答延迟
**最小 36.6ms / 中位 38.0ms / 最大 44.3ms**, 与显示空闲时基本一致 —— 说明画屏已经不占应答路径了.
(这个 ~38ms 是**调试口**测出来的, 里面含固件故意加的 `delay(3)` + 485 帧 flush,
不是总线上的真实延迟; 真实延迟是"收到最后一字节 → 发出应答", 只有几 ms.)

BLE 解锁功能实现不了, 连带的 WiFi AP / Web 扫描页面 (web_server.h / web_pages.h / web_config.h)
已在 2026-10 整体删除; 2026-10-27 **重新引入 WiFi, 但只用于 OTA**:
只开 SoftAP, 不连路由器, 不阻塞等 WiFi —— 原来阻塞等 WiFi 20 秒正是当年被删掉的原因.

资源占用: Flash **80.8% (1535328 B / 1900544 B)**, RAM **20.4% (66844 B)**.
运行时剩余堆 ~111KB (WiFi + BLE 都在跑).

## 5.1 轮速来源开关 (当前: 霍尔实测)

```cpp
#define USE_HALL_SPEED    1      // 0=写死车速, 1=霍尔实测
#define HARDCODE_SPEED_DM 170    // 写死车速 km/h × 10 (170 = 17.0 km/h), 仅 USE_HALL_SPEED=0 时用
```

`USE_HALL_SPEED = 1` —— 车速来自霍尔脉冲, OLED 和协议值都是实测的.

**测速方式: 脉冲间隔, 不是计数窗口.** 1 个磁钢在 17 km/h 下 250 ms 窗口只期望 0.9 个脉冲,
计数窗口读数会在 0 和 ~24 km/h 之间乱跳. 间隔测速 (相邻两脉冲 = 转一圈) 在 17 km/h 时
分辨率约 0.4%:

```
RPM  = 60 / (脉冲间隔秒数 * 磁钢数)
km/h = RPM * 周长(1.28m) * 60 / 1000
```

**但不是直接用"最近一次间隔", 要取最近 5 个间隔的中位数** (2026-10-28 改, 见 §7 的
"偶发没有车速"一行). 中位数天生抗离群值:

| 情况 | 直接用最近间隔 | 用 5 个间隔的中位数 |
|---|---|---|
| 漏一个脉冲 (间隔变 2 倍) | 车速瞬间掉一半 (17 → 8.5) | 不受影响 |
| 传感器毛刺 (间隔被劈成两半) | 车速瞬间翻倍 | 不受影响 |
| 匀速 17 km/h | 17.0 | 17.0 |
| 匀速 3 km/h (蠕行) | 2.8 | 2.8 |

停转判定: **3 s** 内没有新脉冲 → 车速归 0, 状态帧带上驻车标志 (flag_1 的 0x08).
阈值从 2 s 提到 3 s: 3 s 转一圈 = 1.28 m / 3 s = 1.5 km/h, 低于这个速度仪表本来也看不出差别,
但 2 s 的阈值会让 2~3 km/h 的蠕行整段显示 0 (间隔 1.5~2.3 s 正好卡在阈值上).
另外, 如果某个间隔超过 3 s (说明这段时间是停着的), 这一拍的历史全部作废, 车速从 0 重新收敛.

写死模式 (`USE_HALL_SPEED = 0`) 保留, 方便脱离车轮单独调 485 通信链路:
**写死 17.0 km/h → 协议值 35** (线性刻度 round(17×25/12)=35, 仪表显示约 16.8 km/h).

## 6. OTA 升级 (微信小程序局域网直传)

场景: 车停楼下, 人住 10 楼, 车上没网 —— 改个 bug 不该拆车接线 + 手动按 BOOT.

通道: ESP32 开 SoftAP, 手机连上它, 微信小程序通过局域网 HTTP 直接把固件推进来.
能这么干是因为微信小程序的**局域网例外**: url 写成 `${IP}:${PORT}/${PATH}`、
且手机 IP 和目标 IP 同网段时, **不做安全域校验, 也不用 https**.
所以不用备案域名、不用证书、不用云开发, ESP32 也不需要任何公网出口.

> ⚠️ **2026-10-30 起热点默认是关的** (v1.4.0). 平时纯蓝牙, 要 OTA 时小程序**通过蓝牙命令**
> 临时开热点, 推完固件重启就回到默认关. 详见下面 §6.7「蓝牙优先架构」.

| 项 | 值 (ota_config.h) |
|---|---|
| 热点 SSID | `NIU-U1-OTA` |
| 热点密码 | `niu12345` (WPA2 最少 8 位) |
| IP | `192.168.4.1` |
| 端口 | `8080` |
| 分块大小 | 4096 字节 (原始字节, base64 之后 5464 字符) |
| **热点信道** | **11** (不是默认的 1, 见下) |
| 发射功率 | 8.5dBm (`WiFi.setTxPower`, 默认是 19.5dBm) |

### 为什么热点信道必须是 11

BLE 广播固定用 37/38/39 三个信道 (2402/2426/2428MHz), 而 WiFi 默认的信道 1 (2412MHz)
正好压在 BLE 广播信道 37 上 —— 共存时互相干扰, 表现就是**手机能扫到热点但连不上, 或者连上就掉**.
信道 11 = 2452MHz, 离三个 BLE 广播信道都最远, 也避开了路由器常用的 1~6.

另外 `WiFi.setSleep(false)` 关掉 modem sleep, 否则 AP 会时不时把已连的客户端踢掉.

### 为什么发射功率要降到 8.5dBm

手机就贴在车边 (一两米), 功率再高也没用. 而 WiFi 满功率发射的瞬时电流能到 300mA+,
车上是 48V 降压下来的 5V 供电, 功率越小越不容易把板子拉**棕断** ——
棕断 = 反复重启 = 热点掉线 + 屏幕闪烁, 两个症状一个根因.

### 怎么确认手机到底连上没有

固件每秒打一行 `[AP] NIU-U1-OTA 信道11 客户端:N`:

- **N 一直是 0** → 手机压根没关联上 (不是 HTTP 层的问题): 查信道/供电/iPhone 本地网络权限
- **N ≥ 1 但小程序连不上** → 关联上了, 问题在 HTTP 层: 查 iOS 本地网络权限、域名白名单

### HTTP 接口

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| GET | `/ota/info` | - | `{ok, version, slot, state, progress, total, freeHeap, flashUsed, md5, uptime, apOn}` |
| POST | `/ota/begin` | JSON `{size, md5?}` | `{ok}` |
| POST | `/ota/chunk` | body = base64 文本, 头 `X-Offset` = 原始字节偏移 | `{ok, written, total}` |
| POST | `/ota/end` | - | `{ok, restart}` — 校验 + 切槽 + 重启 |
| POST | `/ota/abort` | - | `{ok}` |

### 三个硬约束 (违反必然出错)

1. **POST body 必须 base64**. Arduino WebServer 把 body 存成 `String(plainBuf)` ——
   按 C 字符串处理, **遇 0x00 就截断**, 原始二进制会坏掉. base64 是纯 ASCII 才安全.
   core 的 `base64` 类只有 `encode` 没有 `decode`, 解码器是自己写的 (`ota_server.h` 的 `b64Decode`).
2. `Update.begin(size, U_FLASH)` 自动挑 `esp_ota_get_next_update_partition()` (另一个槽), 不用手动选.
3. **size 必须传准**. 擦除是随写随擦的 (4KB 一扇区, `Updater.cpp` 的 `_writeBuffer`),
   `Update.begin()` 本身不擦 —— 所以传准 size 就不会白擦 1.5MB 分区.

### 失败保护

- 校验不过 / 新固件起不来 → bootloader 回到另一个槽, 老固件照跑 (`Update.end()` 内部 abort)
- 传输中断电 → 备用槽写了一半, 当前槽不受影响, 下次上电照旧
- Arduino 的 Updater 会把开头 16 字节延后写, 写了一半的镜像根本起不来

OTA 期间 OLED 切到 OTA 画面 (SSID + IP + 进度条), 完成后恢复速度画面.
485 不受影响: `server.handleClient()` 非阻塞, 4KB 一块每块只阻塞几 ms, V35 的 200ms 轮询周期不受影响.

### 小程序端

- 源码在仓库根的 `miniprogram/`, 固件由 `tools/build_ota.sh` 打进包里
- **端到端验证 (不用手机)**: `bash tools/ota_push_test.sh` —— 用 curl + base64 模拟小程序全流程,
  传完再 GET `/ota/info` 对版本号
- 上传体验版 / 生成预览二维码: `bash tools/upload_miniprogram.sh preview` / `upload`
  (miniprogram-ci 命令行, 不需要开发者工具; 要 AppID + 上传私钥 + 公网 IP 白名单)

⚠️ **小程序代码包只收白名单扩展名** (.js / .json / .wxml / .wxss / 图片 / 音频 / …),
`.bin` 和 `.txt` **不在白名单里** —— 直接把 `firmware.bin` 放进包里会在上传时被悄悄丢掉,
小程序里读不到. 所以 `build_ota.sh` 把固件转成 base64 塞进 `miniprogram/firmware/firmware.js`.

⚠️ **主包上限 2MB, 所以还得压缩**. 固件 1.58MB → base64 是 2.1MB, 超限.
`tools/lz_pack.py` 是一个极简 LZ77 (68%), 压完 1.05MB → base64 1.4MB, 装得下.
解码在小程序里做 (`miniprogram/utils/lz.js`), 格式见那个文件的头注释.
**改了这个格式, `lz_pack.py` 和 `lz.js` 必须同步改.**

## 6.5 BLE 遥测 (手机不连 WiFi 也能看车速)

OTA 走 WiFi 热点 —— 手机一连热点就断网, 推完固件还得手动切回自己的 WiFi.
看车速不需要断网, 所以另开一条 BLE 通道: 蓝牙直连, 手机照常上网.

固件侧 `src/ble_telemetry.h` (配置在 `src/ble_config.h`):

| 项 | 值 |
|---|---|
| 设备名 | `NIU-U1-BLE` (小程序按前缀 `NIU-U1` 找) |
| Service | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| 遥测特征 | `6e400002-…` notify, 20 字节小端 (前 12 字节是旧格式, 老小程序照样能解) |
| 485 帧特征 | `6e400003-…` notify, 总线上抓到的原始帧 |
| 电池特征 | `6e400004-…` notify, 电池信息 (BMS 解析结果, 分片消息) |

> **BLE 名字为什么改成 `NIU-U1-BLE`** (2026-10-29): 原来跟 WiFi 热点同名 (`NIU-U1-OTA`),
> 在手机的蓝牙列表里跟 WiFi 网络混在一起分不清. 小程序那边只按前缀 `NIU-U1` 匹配, 不受影响.

### 用蓝牙要做什么准备

**不需要**先在系统设置里配对/连接 —— BLE 是直连, 小程序自己发起.
但权限必须给, 否则小程序会直接失败:

| 平台 | 要做什么 |
|---|---|
| iOS | 系统蓝牙开着; **微信** 要有蓝牙权限: 设置 → 隐私与安全性 → 蓝牙 → 微信. 第一次点「连接」时微信会弹「微信想要使用蓝牙」, 点允许 —— 如果之前点了拒绝, 就得手去设置里改. (推固件还要 iOS 的「本地网络」权限, 那是另一条) |
| Android | 系统蓝牙开着; 微信要「附近设备/蓝牙」权限; **扫蓝牙还要「定位」权限** (Android 6+ 强制), 不给就一个设备都扫不到 |

小程序侧已经把微信的 errMsg 翻译成能动手解决的提示了 (`miniprogram/utils/ble.js` 的 `explainBleFail`),
而且扫不到时会把它**实际扫到的设备名列出来** —— 要是列表里有 `NIU-U1-BLE` 却还是连不上,
那就是权限问题, 不是设备问题.

遥测载荷 (20 字节小端):

| 偏移 | 字段 | 含义 |
|---|---|---|
| 0-1 | speed_dm | 车速 ×10 (霍尔实测) |
| 2-3 | rpm | 轮速转速 |
| 4-5 | voltage | 电压 ×10 (V) |
| 6-7 | current | 电流 ×10 (A, 有符号) |
| 8 | protocol_speed | 485 协议车速值 (0-127) |
| 9 | error | 错误码 |
| 10 | unlocked | 1 = 已解锁 |
| 11 | flags | bit0: 刚收到过 485 帧 |
| 12-13 | q_count | 收到 V35 状态查询的次数 |
| 14-15 | a_count | 我们回出的应答次数 (应与 q_count 相等) |
| 16-17 | pulse_count | 霍尔脉冲累计数 (低 16 位) |
| 18 | bad_cs | 校验和不对的帧数 |
| 19 | interval_x10 | 最近一次脉冲间隔 (10ms 单位) |

后 5 个字段是**诊断用的**: 骑车时看小程序就能分清是谁的问题 ——
轮询数一直涨 = 总线通; 应答数跟着涨 = 我们答上了; 脉冲数不涨 = 霍尔/磁钢没信号, 车速自然是 0.
(计数是 16 位会回绕, 小程序端按差值算速率.)

485 帧一帧最长 64 字节, 蓝牙一包最多 20 字节 → 分块推, 小程序端攒到 `0x16` (帧尾) 为止算一整帧.

### 电池信息 (BMS) 的消息格式

一条特征上跑三种消息, 每条通知带 3 字节头 `[类型][片号][总片数]`, 类型 1=状态 2=单体电压 3=型号串.
状态 17 字节: 标志 / 电量% / 总电压0.1V / 电流0.1A / 温度个数 / 5×温度 / 单体串数 / 最低单体mV / 最高单体mV.
单体电压: 每格 2 字节 mV. 型号串: ASCII.
打包代码在 `src/ble_battery_msg.h` (纯 C++, 不依赖 Arduino, 可以在 PC 上编译跑测试).

**两端对得上的验证方法** (不用车, 不用板子): 固件的打包函数 `bleBatteryPack*` 在 PC 上编译,
把真车抓包里的 BMS 报文解出来打成分片 → 喂给小程序的 `handleBatteryChunk` → 出来的值
必须跟原始报文一致. 这个校验把「固件改了格式但小程序没跟着改」这类错挡在上传之前.

**坑: 分片要按"收齐了几片"算, 不能按"收到几次"算**: 蓝牙会重传, 同一片来两次的话,
按次数算会提前凑够总片数, 拼出来的数据少一片 —— 而固件侧是"变了才推", 这条消息就永远补不回来了.

### 坑: 断连以后不会自动重新广播

Arduino 的 `BLEServerCallbacks::onDisconnect` 里调 `advertising->start()` **没用** ——
那个回调跑在蓝牙任务里, 这时候 GAP 状态机还没处理完断连, 启动广播被静默丢掉,
结果就是**设备再也不广播, 手机再也扫不到它** (实测踩过: 连一次之后设备就"消失"了).

必须把重新广播**延后到主循环** (`ble_telemetry.h` 的 `handle()` 里, 断开 300ms 之后再启动).
另外加了兜底: 断开超过 30 秒还没广播出去就再试一次.

### 坑: 重连后单体电压和型号串不再推送

单体电压和型号串是**变了才推** (哈希比对), 但手机重连后小程序那边的状态是空的 ——
哈希没变, 这两个消息就永远不会再发, 结果电池面板只剩状态, 没有单体条也没有型号串.
所以 `handleDisconnect()` 里要把两个哈希清零, 让重连后的第一次通知重新推一遍.

### 其它注意

- Arduino-ESP32 2.0.17 自带的 `BLE` 库在 C3 上能编能跑 (Bluedroid, 无经典蓝牙),
  PlatformIO 不用额外配置就能找到它. 但它吃内存: bluedroid 初始化要几十 KB 堆,
  所以 `begin()` 放在 setup 最后, 失败也不影响 485.
- WiFi SoftAP + BLE 可以同时开 (C3 单射频, IDF 负责时分), 实测 OTA 传输期间 BLE 照常工作.
- 蓝牙协议栈占 ~700KB flash —— 这是分区表要扩容到 1.75MB/槽的直接原因.

## 6.6 电池 BMS 报文解析 (2026-10-28 加)

485 是半双工总线, 所有节点都能听到别人说的话 —— V35 问 BMS「电量多少」,
BMS 的应答我们虽然不是收信人, 但在总线上照样能收到. 于是把它解析出来给小程序看.

**我们不冒充 BMS, 也不应答任何 BMS 请求** —— 只听.

### V35 怎么问 BMS

V35 用功能码 `0x02` 加两个字节问 BMS, BMS 用 `0x82` 回. 反混淆 (每个字节 -0x33) 后:

| V35 的请求 | BMS 应答长度 | 内容 |
|---|---|---|
| `2d 0f` | 15 | 电池状态 (每次轮询都问, 约 3 次/秒) |
| `09 24` | 36 | 型号串 |
| `02 2b` | 43 | 型号串 (前面多 7 字节头 `14 04 55 55 55 55 01`) |
| `3c 28` | 40 | 单体电压 |

### 15 字节状态帧的字段布局

| 字节 | 含义 | 单位 |
|---|---|---|
| `[0..1]` | 总电压 (**大端** u16) | 0.1V (`0x0219` = 537 → 53.7V) |
| `[2..4]` | 未知 | |
| `[5]` | 电流 | A (实测 0..38) |
| `[6]` | 电量 | % |
| `[7..9]` | 未知 | |
| `[10..14]` | 5 个温度 | °C |

### 40 字节单体电压帧

前面是单体电压 (**大端** u16, 单位 mV), 一直到第一个 0 为止, 后面是保留的 0.
13 串的 48V 电池 = 13 × 3.7V, 加起来跟状态帧的总电压对得上 (交叉验证过).

### 型号串

36 字节那帧串在开头, 43 字节那帧串在第 7 字节之后. 16 字节 ASCII, 形如
`BUS9LN2S60900065` / `BUM9L62S43500598`.

### 字段布局的来源与验证

布局来自 [xzfn/scooter-repair](https://github.com/xzfn/scooter-repair) 的 `docs/niu-u-civic.md`
「BMS返回的主要是电量」一节, 并用该仓库的真车抓包日志**逐字段核对过**:
7 个日志文件共 2041 帧 BMS 报文, 解析成功率 100%, 校验和错误 0,
状态帧的总电压跟单体电压求和一致 (48.6V vs 48.69V, 53.3V vs 53.4V).

### 改了 485 的分帧方式 ⚠️

原来靠 `0x16` 找帧尾, 现在改成**靠长度字节**: 第 6 个字节是数据长度, 整帧 = `6 + len + 2`.
原因: 数据区里也可能出现 `0x16` (明文 `0xE3` + `0x33` 混淆后正好是 `0x16`),
靠 `0x16` 分帧会把一帧劈成两半, 后面那半被当成新帧 → BMS 应答解析不出来.
分帧代码在 `.ino` 的 `rxPush()` / `rxResync()`.

### 调试: 没有车也能验

调试口 (`/dev/ttyUSB0`) 里敲 `[TX] 68 31 CE 68 82 0F ... 16` 回车, 就把这帧喂进 485 解析链路,
不用拆车接线就能验证 BMS 解析. 代码在 `.ino` 的 `DEBUG_INJECT_485` 块 (编译期开关).

## 6.7 蓝牙优先架构 (2026-10-30 加, v1.4.0)

**一句话: 平时只用蓝牙, WiFi 只在 OTA 那几分钟开一下.**

### 为什么改

原来的设计是开机就开 WiFi 热点, 小程序靠 HTTP 推固件. 问题:

1. **手机一连热点就断网** —— 推固件的时候手机上不了网
2. **SoftAP 一直在发信标, 白耗电** —— 车上是电池供电
3. **两边射频同时用, BLE 广播节奏会被共存调度影响** —— 手机扫码慢
4. OTA 一年碰不到几次, 没必要常开

改成: **WiFi 默认关** (`ota_config.h` 的 `OTA_AP_DEFAULT_OFF 1`), 小程序要升级时
**通过蓝牙发一个字节把热点临时打开**, 推完固件板子重启, 自然回到默认关的状态.

### 蓝牙命令通道

新增特征 `6e400005-b5a3-f393-e0a9-e50e24dcca9e` (write + read + notify):

| 字节 | 含义 |
|---|---|
| `0x57` (`'W'`) | 开 OTA 热点 |
| `0x58` (`'X'`) | 关 OTA 热点 |

小程序侧 (`miniprogram/utils/ble.js`): `writeCommand(deviceId, cmdChar, 'W')`.
固件侧 (`ble_telemetry.h`): `BleCmdCb::onWrite` 收到后**只排队**, 由主循环 `handle()` 执行 ——
BLE 回调跑在蓝牙任务里, 在那边动 WiFi 会跟共存调度打架.

### 三个必须知道的坑

**1. 写命令必须用带 param 的 `onWrite` 重载**

```cpp
void onWrite(BLECharacteristic* ch, esp_ble_gatts_cb_param_t* param) override;
```

废弃版 `onWrite(pCharacteristic)` 里的 `getValue()` **拿不到刚写进来的字节** ——
实测写 `0x57` 读回来是 `0x00`. 要用 `param->write.value[]`.

**2. 命令字节取最后一个, 不是第一个**

`gatttool` 之类的工具写 `0x57` 会被当成 2 字节大端 (`00 57`), 取头就拿到 `0x00` 了.
小程序用的是 `wx.writeBLECharacteristicValue` (原始 ArrayBuffer), 不会有这问题,
但固件取最后一个字节更保险.

**3. 重新开热点时 HTTP server 必须重绑**

`WebServer::begin()` 内部先 `close()` 再监听, 所以 `startAP()` 里**每次都调** `bindServer()`.
不重绑的话「关热点再开」之后 HTTP 端口收不到任何请求 (lwIP 被 `WIFI_OFF` 拆过, 老 socket 废了).

### 关热点不能用 `WiFi.mode(WIFI_OFF)`

`WIFI_OFF` 会走 `espWiFiStop()` → `esp_wifi_stop()` + lwIP 反初始化, **整个 WiFi 协议栈被拆掉**.
改成只切模式: `esp_wifi_set_mode(WIFI_MODE_NULL)` —— 热点停止广播, 协议栈留着,
`startAP()` 随时能开回来.

### 广播包布局 (iPhone 能不能扫到的关键)

| 包 | 内容 |
|---|---|
| 主广播包 | Flags(0x06) + 完整设备名 (10 字节) |
| 扫描回应 | 完整设备名 + 128 位 Service UUID (共 30 字节, 在 31 字节上限内) |

**名字必须在主广播包里.** 库默认行为是把名字和 UUID 全塞扫描回应, 主广播包只有 Flags ——
而扫描回应只有**主动扫描**才收得到 (手机发 SCAN_REQ). iPhone 后台的小程序是**被动扫描**,
收不到扫描回应, 看到的就是"一个没名字的设备", 直接被名字过滤掉.
Linux 用主动扫描所以一直能看到 —— 台架上测不出这个坑.

扫描回应里加 UUID 是为了"按服务 UUID 过滤"的扫描器也能匹配上. 注意 31 字节上限:
Flags(3) + 名字(12) + UUID(18) = 33 **超了**, `addData` 会静默丢弃 ——
所以扫描回应里**不放 Flags**, 刚好 30 字节.

### 实测数据 (2026-10-30, 台架)

用 `hcitool lescan --duplicates` 抓 12 秒原始广播包:

| 状态 | 广播包数 | 折算频率 |
|---|---|---|
| WiFi 关 | 100 | ~8.3/秒 (间隔 ~120ms) |
| WiFi 开 | 117 | ~9.75/秒 |
| WiFi 开 + 有客户端在线 | 117 | ~9.75/秒 |

> ⚠️ **踩过的坑: 别用 btmon 的次数下结论.** btmon 抓的是控制器**重复过滤之后**的上报,
> 看起来像"16 秒才广播一次" —— 那是过滤器的假象, 不是真的限流.
> 要看真实节奏必须用 `hcitool lescan --duplicates` (要 root, 且要先停 bluetoothd).

### 台架已验证

- BLE 写 `0x57` → 热点起来 (信道 11 / 192.168.4.1:8080) ✅
- BLE 写 `0x58` → 热点关 ✅
- 开→关→开→关 连做 4 次, 无 panic 无复位 ✅
- 广播包内容用 btmon 核对过: 主广播包带完整名字 ✅

**没验证的**: HTTP 端到端 (这台开发机的无线网卡扫不到 2.4GHz, 连不上 ESP32 热点),
需要用户在车上用小程序实测.

| 状态帧长度/字段错位 | ✅ 修 | 原厂 `0x02 05 08` 应答是 **12 字节**, 车速在**第 9 字节** (协议值 0-127, 线性刻度 kmh×25/12), 之前回 14 字节且把速度放在 [3][4], ECU 读不到车速还会报错误码 190 |
| GPIO2 占用 | ✅ 修 | strapping pin, 485 RX 挪到 GPIO4, TX 挪到 GPIO7 |
| **偶发没有车速** | 🔄 2026-10-28 改 | 协议侧逐字节核对过是对的 (见下面的"偶发没有车速"专项), 所以问题在测速和时序两处: ① 测速改成最近 5 个间隔取**中位数**, 漏一个脉冲不再让车速掉一半; 停转阈值 2s→3s, 2~3km/h 的蠕行不再整段显示 0. ② 485 应答路径去掉 `Serial.flush()` —— USB 接上电脑时 flush 最长阻塞 100ms, 而 V35 单次轮询超时只有 ~20ms, 卡一次这一轮就变成"没应答→错误码 190→车速 0". ③ 收到帧先校验和再决定要不要答, 噪声帧不再被当成查询. 另外加了诊断字段, 小程序上能直接看出是总线还是霍尔的问题 |
| **WiFi 连不上 + 屏幕一会亮一会不亮** | 🔄 2026-10-29 改 | 见 §7.2 专项. 根因是 OLED 画屏放在 `loop()` 里 (100kHz 下一屏 95ms), loop 被占掉 ~95% 的时间, 连带把 485 应答和 WebServer 一起饿死. 改法: 画屏挪到独立任务 + I2C 提到 400kHz; 热点信道 1→11 (避 BLE 广播信道 37); WiFi 发射功率降到 8.5dBm. 屏幕常驻显示 `rst:` 复位原因, 车上要是还在闪, 看这一行就知道是不是在反复复位 |
| BLE 防丢器自动解锁 | ❌ 已放弃 | 红米 Watch 3 广播窗口太短 + iPhone 侧无法配合, 实现不了, 已移除 |
| NFC (PN532) 无钥匙解锁 | ❌ 已移除 | 2026-10-22 删除驱动代码/接线文档/库依赖, I2C 只留板载 OLED |
| 485 FOC 解锁 CRC16 (poly 0x7085) | ❌ 未实现 | 真正的 FOC 解锁需要 CRC16 算 token, 现在只处理 0x01 unlock 命令立即返回成功 |
| OTA 通道 | ✅ 硬件实测通过 | 固件侧用 `tools/ota_push_test.sh` 推过好几次 (含 1.58MB 的 BLE 固件), 分区切换正常; 小程序真机行为还没实测 (这台机器没有微信开发者工具也没有 iPhone) |
| 485 分帧靠 0x16 找帧尾 | ✅ 修 | 数据区里也可能有 0x16 (明文 0xE3 + 0x33), 会把帧劈成两半 → 改成按长度字节定帧 (见 §6.6) |
| 电池 BMS 报文 | 🔄 待上车实测 | 解析器用真车抓包的 2041 帧 BMS 报文逐字段核对过 (100% 解析成功, 校验和 0 错); BLE 打包格式也跟小程序端对过; 但**装到车上抓真实 BMS 报文还没测** (板子当时没接在车上的 485 总线上) |
| BLE 断连后不广播 | ✅ 修 | 在 `onDisconnect` 回调里重启广播会被静默丢掉, 必须延后到主循环 (见 §6.5) |
| **iPhone 扫不到 NIU-U1-BLE** | 🔄 2026-10-30 改 | 见 §7.3 专项. 三个原因都修了: ① **广播包布局** —— 名字必须放主广播包 (iPhone 后台是被动扫描, 收不到扫描回应); ② **小程序传 `services: []`** —— iOS 上会被当成过滤条件, 把没广播服务 UUID 的设备全过滤掉, 改成不传; ③ **固件可能进入"活着但不广播"** —— 加了定期重启广播兜底. 另外把 WiFi 改成默认关 (蓝牙优先, 见 §6.7). **真机 iPhone 还没实测** |
| BLE 重连后单体电压/型号串不再推 | ✅ 修 | 这两条是"变了才推", 重连后手机状态是空的 → 断连时清哈希 (见 §6.5) |
| iOS 本地网络权限 | ⚠️ 注意 | iOS 14+ 第一次连热点时微信会弹「本地网络」授权, 要点允许, 否则小程序发不出请求 |
| 安卓 BLE 扫描要定位权限 | ⚠️ 注意 | Android 6+ 扫蓝牙要「定位」权限, 不给就扫不到设备 |

### 7.1 "偶发没有车速" 的排查过程 (2026-10-28)

现象: 仪表 (和小程序) 偶发不显示车速, 别的实现 (glm5.2 的 FOC 模拟器) 却"跑起来没问题,
会有稳定的速度恢复". 先怀疑协议, 逐条核对后发现协议侧是对的:

**协议侧核对结论 (用 xzfn/scooter-repair 的真车抓包逐字节对)**

| V35 发给 FOC 的 | 原厂 FOC 回的 | 我们回的 | 一致? |
|---|---|---|---|
| `01 01` (状态标志) | `81 01 \| 00` (1 字节) | 同 | ✅ |
| `01 01 \| 02` (版本) | `81 10 \| "U1E02V11U1E02V11"` | 同 | ✅ |
| `01 01 \| 03` (MU 号) | `81 10 \| "MU13482B42510971"` | 同 (16 字节) | ✅ |
| `01 01 \| 04` (固件版本) | `81 01 \| 11` | 同 | ✅ |
| `05 02` (解锁 CRC16) | `85 01 \| ce` | 同 | ✅ |
| `06 01 \| 11` (周期配置, ~1.2s 一次) | `86 00` (空数据) | 同 | ✅ |
| `02 02 \| 05 08` (问车速, ~200ms 一次) | `82 0c \| 30 26 3c 01 00 19 00 00 00 00 08 00` | 同 | ✅ |

几个容易踩的点:

- **数据区是 ±0x33 混淆的**: V35 发的 `02 02 38 3b` 反混淆后才是 `05 08`;
  我们回的时候也要 +0x33 再发出去.
- **校验和是从帧头累加到 CS 前一字节取低 8 位** (不是 CRC):
  `68 20 df 68 82 0c 63 59 6f 34 33 4c 33 33 33 33 3b 33` 的 CS = 0x75 ✓ (我们的算法一致).
- **应答帧带的是自己的地址对** `20 DF`, 不是请求方的 `40 BF`.
- **12 字节状态帧里车速在第 9 个字节** (下标 9), 有符号 int8, 负数=倒挂;
  ECU 侧换算 `仪表速度 = 值×12/25`, 负值直接归零.
- **应答长度必须精确**: `05 08` 回 12 字节, `05 09` 回 14 字节, 长度不对 ECU 整帧丢弃.
- V35 的单次轮询超时只有 **~20ms** (真车抓包里从发问到收到应答稳定 21ms), 应答必须快.

既然协议是对的, 剩下的就是测速和时序 (见 §7 表格里"偶发没有车速"那一行).

**怎么在车上确认是哪一类问题**: 小程序"诊断"卡片 (固件 1.3.0 起)

| 现象 | 结论 |
|---|---|
| 轮询数一直涨, 应答数也涨, 但脉冲数不涨 | 霍尔/磁钢没信号 —— 车轮在转但传感器没出脉冲 |
| 轮询数涨, 应答数不涨 | 我们没答上 (校验和错误帧会累计) |
| 两个数都不涨 | 485 总线没通 (接线/地址/波特率) |
| 脉冲数在涨, 车速却是 0 | 磁钢位置/极性不对, 或者停转阈值判定错了 |

## 7.2 "WiFi 连不上 + 屏幕一会亮一会不亮" 的排查过程 (2026-10-29)

用户反馈: 刷了带 OTA 的固件之后, 手机连不上热点, 而且屏幕一会亮一会不亮.

**三个症状, 其实是同一个根因**: 加了 WiFi + BLE 之后固件从 320KB 涨到 1.58MB,
但真正的问题在 OLED —— 画屏一直放在 `loop()` 里, 而一屏 1024 字节在 I2C 100kHz 下要传 **95ms**.
于是 `loop()` 有 95% 的时间在画屏, 什么都干不了, 连带三个后果:

| 被饿死的东西 | 表现 |
|---|---|
| 485 收包 + 应答 | V35 单次轮询超时只有 ~20ms → 这一轮"没应答" → 错误码 190 + 车速 0 |
| `otaService.handle()` (WebServer) | 手机连上热点了, 但 HTTP 请求发不出去 → "wifi 连不上" |
| 屏幕内容 | 在"正常车速"和"错误码 190"之间来回变 → 看着就是**屏幕在闪** |

**改动 (固件 1.3.1)**:

1. **画屏挪到独立 FreeRTOS 任务** (`oledTask`, 优先级 1, 栈 4096, 周期 200ms).
   loop 每 100ms 只把快照写进 `disp_state` (互斥量保护), I2C 全在 OLED 任务里做.
   优先级跟 Arduino 的 loop 任务同级, 靠时间片轮转, 不会饿死应答.
2. **I2C 从 100kHz 提到 400kHz** (1024 字节 95ms → ~25ms), 并在 include u8g2 **之前**
   `#define U8X8_DO_NOT_SET_WIRE_CLOCK` —— 不然 u8g2 每传一页都会把时钟改回 100kHz.
3. **热点信道 1 → 11**: 默认信道 1 (2412MHz) 压在 BLE 广播信道 37 (2402MHz) 上,
   共存时手机能扫到热点但连不上/连上就掉. 信道 11 (2452MHz) 离三个 BLE 信道都最远.
4. **WiFi 发射功率 19.5dBm → 8.5dBm** + `WiFi.setSleep(false)`:
   手机就贴在车边, 功率再高没用; 满功率发射瞬时电流 300mA+, 车上是 48V 降压供电,
   功率小了不容易棕断 (棕断 = 反复重启 = 热点掉线 + 屏幕闪, 一个根因两个症状).
5. **屏幕常驻显示 `rst:<复位原因>`** (开机画面里也显示): 上次是 POWERON / SW / PANIC /
   TASK_WDT / BROWNOUT. 车上要是还在闪, 这一行直接告诉你是不是在反复复位.

**台架验证** (模拟 V35 每 200ms 发一帧, 显示满负荷重画): 60/60 应答,
延迟最小 36.6ms / 中位 38.0ms / 最大 44.3ms —— 与显示空闲时一致, 说明画屏已经不占应答路径了.

**还没验证的**: 这台机器的无线网卡扫不到 2.4GHz (只扫得到 5GHz), 也没有 iPhone,
所以 **SoftAP 的真实可连性没法在台架上测**, 只能上车试.
上车时按这个顺序看:

1. 屏幕上的 `rst:` 是不是 PANIC / BROWNOUT —— 是的话是反复复位, 先查供电
2. 手机能不能**列出** `NIU-U1-OTA` 这个热点 —— 列不出 = 信号/供电/信道问题
   (蓝牙那边是 `NIU-U1-BLE`, 两个名字不一样, 别找错)
3. 列得出但连不上 = 信道或共存问题
4. 连上了但小程序连不上 → 看小程序日志, 它会提示 iOS 本地网络权限 / 域名白名单
5. 插上 USB 看串口里的 `[AP] ... 客户端:N` —— N 一直是 0 就是压根没关联上

## 7.3 "iPhone 扫不到 NIU-U1-BLE" 的排查过程 (2026-10-30)

用户反馈: 用小程序升级完固件之后, iPhone 的蓝牙列表里**看不到** NIU-U1-BLE,
只能看到别的设备 (TCL 电视). 小程序的报错也没变化.

**排查第一步: 确认板子本身正常.** 台架上 `bluetoothctl` 能扫到 `NIU-U1-BLE` (RSSI -44 ~ -52dBm),
`bluetoothctl connect` 也能连上, 四个特征 + 2902 描述符都在. 所以**固件和手机之间的射频没问题**.

**第二步: 读 flash 确认跑的是哪版固件.** `esptool read_flash` 把两个槽都读出来对比:

- app0 (0x10000): 版本串 `1.3.1`
- app1 (0x1E0000): 版本串 `1.3.2`, 头 16KB 与小程序包里的固件**逐字节相同**
  (说明 OTA 确实写进去了)

app0 与 1.3.2 的包整包只差 **66 个字节** (32 字节编译哈希 + 版本号 3 个字符 + 尾部哈希),
也就是说**代码完全一样** —— 1.3.1 那次构建就已经包含了广播布局的改动. OTA 生效了.

**第三步: 看广播包到底长什么样.** `btmon` 抓 HCI:

```
LE Advertising Report (0x02)
  Event type: Connectable undirected - ADV_IND (0x00)
  Address: E8:3D:C1:8D:D4:06
  Data length: 15
  Flags: 0x06
  Name (complete): NIU-U1-BLE
```

名字在包里的. 那为什么 iPhone 看不到?

**根因: iPhone 后台小程序是「被动扫描」, 而被动扫描收不到扫描回应 (SCAN_RSP).**

蓝牙分两种扫描:
- **主动扫描**: 手机发 SCAN_REQ, 外设回 SCAN_RSP —— 能拿到扫描回应里的内容
- **被动扫描**: 手机只听广播包 (ADV_IND) —— **扫描回应里的东西一概收不到**

Arduino BLE 库的默认布局是「主广播包只放 Flags, 名字和 UUID 全塞扫描回应」.
Linux 的 `bluetoothctl` 用主动扫描, 所以一直看得到 —— **台架上测不出这个坑**.
而 iPhone 上微信小程序在后台用的是被动扫描, 拿到的只有 Flags 没有名字,
按名字前缀 `NIU-U1` 一过滤就把它扔了.

**改动 (固件 1.4.0)**:

1. **自定义广播包**: 主广播包 = Flags(0x06) + 完整设备名; 扫描回应 = 名字 + 128 位 UUID
   (用 `BLEAdvertisementData` + `setAdvertisementData` / `setScanResponseData`).
   名字必须放主广播包 —— 所有扫描方式都收得到.
2. 扫描回应里加 UUID 是为了"按服务 UUID 过滤"的扫描器也能匹配上.
   注意 31 字节上限: Flags(3)+名字(12)+UUID(18)=33 超了会被静默丢弃, 所以扫描回应里**不放 Flags**.
3. **WiFi 改成默认关** (蓝牙优先, 见 §6.7) —— 顺带解决"手机连热点就断网"和功耗.
4. 广播间隔显式设成 100~150ms (`setMinInterval(160)` / `setMaxInterval(240)`).

**一个自己踩的坑: 用 btmon 的次数下结论会错.** 中途 btmon 显示"ESP32 16 秒才广播一次"
(14.3s / 30.3s / 46.3s / 62.3s 各一次), 一度以为是共存调度限流, 还据此改了架构.
用 `hcitool lescan --duplicates` 抓**原始**广播包才看明白:

| 状态 | 12 秒内广播包数 | 折算 |
|---|---|---|
| WiFi 关 | 100 | ~8.3/秒 |
| WiFi 开 | 117 | ~9.75/秒 |
| WiFi 开 + 有客户端在线 | 117 | ~9.75/秒 |

**广播一直正常.** btmon 抓的是控制器**重复过滤之后**的上报, 那个"16 秒"是过滤器的假象.
(查共存问题必须用 `hcitool lescan --duplicates`, 要 root 且先停 bluetoothd.)

**台架已验证**: 广播包内容用 btmon 核对过 (主广播包带完整名字);
BLE 开/关热点命令通路打通; 开→关→开→关 循环 4 次无 panic.

**还没验证的**: iPhone 真机行为. 这台机器没有 iPhone, 而且无线网卡扫不到 2.4GHz,
连 ESP32 热点都连不上 —— **HTTP 端到端也没法在台架上验**, 需要用户实测.

### 7.3.1 补充: iPhone 能看到别的设备, 却看不到我们的 (2026-10-30 晚)

用户反馈: **iPhone 的蓝牙列表能看到笔记本的 `wangxuhui-QTC6`, 就是看不到 NIU-U1-BLE**.
这说明**手机的蓝牙接收本身没问题** —— 问题在我们这一侧.

排查后又发现两个 iOS 特有的坑:

**坑 1: 微信小程序在 iOS 上传 `services: []` 会把设备全过滤掉**

微信文档说 `wx.startBluetoothDevicesDiscovery` 的 `services` 是"要搜索的广播包里有对应 UUID 的主服务的设备".
iOS 的实现里, **传空数组被当成"过滤条件存在"**, 结果只上报广播里带服务 UUID 的设备.
而我们的主广播包只有 Flags + 名字 (名字必须放主广播包, 见上), 128 位 UUID 在扫描回应里 ——
**正好被这个过滤挡掉**. 安卓的语义不同, 所以安卓能扫到、iPhone 扫不到.

修法: **小程序侧干脆不传 `services`**, 扫到全部再在 JS 里按名字前缀筛.

**坑 2: 固件可能进入"活着但不广播"的状态**

BLE 的重新广播有坑: `advertising->start()` 有可能正好撞上 GAP 状态机没准备好而被**静默丢掉**
(代码却以为成功了). 一旦这样, 板子活着、485 正常、WiFi 正常, 但**BLE 再也不广播**,
手机永远扫不到 —— 而且这个状态在车上没法自查.

修法: 固件里加**定期重启广播** (没连手机时每 15 秒一次, `BLE_REBROADCAST_PERIOD_MS`),
保证广播一定活着. 串口会打 `[BLE] 广播重启 (定期兜底)`.

**顺带: 小程序报错现在会列出扫到的每一个设备** (名字 + MAC + RSSI + 广播的 UUID),
以及**微信缓存里的设备** (`wx.getBluetoothDevices`). iOS 对同一个设备地址的 GATT 缓存很顽固 ——
之前连接失败过的话, 之后可能一直连不上, 这时能看到"设备在缓存里但连不上"这种 iOS 特有的坑.

上车后按这个顺序看:

1. iPhone 设置 → 蓝牙, 能不能看到 NIU-U1-BLE (在"其他设备"里, 不是"我的设备")
2. 微信 → 小程序 → 车辆状态页, 点连接, **把弹出的完整报错发回来** (现在会列出扫到的所有设备)
3. 固件升级页 → 点「用蓝牙开热点」, 看热点能不能起来 (串口会打 `[OTA] 热点 ... 已启动`)

## 8. 调试技巧

- **看 485 收**: loop() 里 `[485←]` 逐字节回显, 帧尾 0x16 换行
- **看 485 发**: `sendFrame()` 里 `[485→]` 回显整帧
- **看轮速**: `foc_status.wheel_rpm` / `wheel_speed_dm` (十分位整数), OLED 上直接显示
- **看状态**: `[状态] 已解锁 | 轮速:xxRPM | x.xkm/h` 每 3 秒一次
- **看电池**: `[BMS] 53.3V  0A  电量 100%  温度 30/30/30/30/29  单体 13 串 4.088~4.114V` 每秒一次
- **没车也想验 BMS 解析**: 串口里敲 `[TX] 68 31 CE 68 82 0F ... 16` 回车, 字节直接喂进 485 解析链路 (见 §6.6)
- **想看 485 完整原始帧**: `od -A x -t x1 /dev/ttyUSB0` 旁路串口工具 (需要 USB-485 转换器)
